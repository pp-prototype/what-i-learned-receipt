# What I Learned Receipt 개선 프로젝트 작업 범위 및 기능 명세

## 1. 문서 개요

- 문서 목적: 기존 정적 이미지 발행 도구를 사용자별 프로젝트 기록 서비스로 확장하기 위한 작업 범위와 기능 요구사항을 정의한다.
- 대상 버전: MVP 2.0
- 주요 독자: 기획자, 디자이너, 개발자, 운영자
- 작성 기준: 2026-07-24

## 2. 프로젝트 배경

현재 `what-i-learned-receipt`는 사용자가 당일 사진 한 장과 짧은 학습 내용을 입력하고 PNG 영수증을 생성하는 단일 페이지 정적 웹이다.

현재 제품은 설치와 서버 운영 없이 빠르게 기록 이미지를 만들 수 있다는 장점이 있으나, 다음과 같은 한계가 있다.

- 로그인과 사용자 구분이 없다.
- 작성 내용과 사진이 저장되지 않는다.
- 프로젝트별로 기록을 분류할 수 없다.
- 과거 기록을 조회하거나 수정할 수 없다.
- 입력 화면과 최종 영수증 미리보기가 분리되어 있지 않다.
- 공개 기록을 검토하고 승인하는 운영 기능이 없다.

이번 개선 프로젝트에서는 기존의 간결한 정적 웹 경험과 PNG 발행 기능을 유지하면서, 사용자별 기록 축적 기능을 추가한다.

## 3. 제품 목표

### 3.1 핵심 목표

1. 사용자가 로그인하여 자신의 기록을 안전하게 관리할 수 있다.
2. 사용자가 여러 프로젝트를 만들고 프로젝트별로 사진과 학습 기록을 축적할 수 있다.
3. 저장된 기록을 다시 조회하고 수정하며 PNG 이미지로 발행할 수 있다.
4. 모바일 환경에서 사진 촬영부터 기록 저장까지 자연스럽게 완료할 수 있다.
5. 프론트엔드는 정적 웹 배포 방식을 유지하고 별도의 상시 애플리케이션 서버 운영을 최소화한다.

### 3.2 성공 지표

초기 배포 후 다음 지표를 확인한다.

- 로그인 완료율
- 프로젝트 생성 완료율
- 기록 작성 시작 대비 저장 완료율
- 사용자당 주간 기록 저장 수
- 저장된 기록의 재조회율
- PNG 발행 또는 공유 실행률
- 사진 업로드 실패율
- 기록 작성 중 이탈률

초기 MVP에서는 정량 목표값을 고정하지 않고 기준 데이터를 먼저 수집한다.

## 4. 제품 원칙

### 4.1 저장과 발행의 분리

- `기록 저장`은 사용자 개인 공간에 내용을 보관하는 행위다.
- `이미지 만들기`는 저장한 기록을 PNG로 생성하거나 공유하는 행위다.
- `공개 요청`은 개인 기록을 공개 영역에 게시하기 위해 운영 검토를 요청하는 행위다.

세 행위는 서로 독립적으로 제공한다.

### 4.2 비공개 우선

- 새 프로젝트와 기록은 기본적으로 비공개다.
- 사용자의 명시적인 요청 없이는 기록을 공개하지 않는다.
- 관리자는 공개 승인 요청이 없는 개인 기록을 일상적인 검수 대상으로 사용하지 않는다.

### 4.3 모바일 우선

- 핵심 작성 흐름은 모바일 세로 화면을 기준으로 설계한다.
- 주요 버튼의 터치 영역은 최소 44px 이상을 권장한다.
- 사진 업로드, 저장, 공유 상태를 사용자가 즉시 이해할 수 있어야 한다.

### 4.4 기존 정체성 유지

- 영수증 또는 엽서 형태의 결과물은 제품의 대표적인 시각 요소로 유지한다.
- 기존 iOS 공유 시트와 데스크톱 PNG 다운로드 동작을 유지한다.
- 기능이 추가되더라도 짧고 빠르게 기록한다는 사용 경험을 우선한다.

## 5. 사용자 및 권한

### 5.1 사용자 유형

| 사용자 유형 | 설명 |
| --- | --- |

| 일반 사용자 | 자신의 프로젝트와 기록을 관리하는 로그인 사용자 |

### 5.2 권한 원칙

| 기능 | 비로그인 | 일반 사용자 | 관리자 |
| --- | ---: | ---: | ---: |
| 서비스 소개 조회 | O | O | O |
| 로그인 | O | - | - |
| 자신의 프로젝트 조회·관리 | X | O | O |
| 자신의 기록 조회·관리 | X | O | O |
| 다른 사용자의 비공개 기록 조회 | X | X | 원칙적으로 X |
| 공개 승인 요청 | X | O | O |

| 기록 승인·반려·공개 중지 | X | X | O |

관리자 권한은 화면 노출 여부가 아니라 데이터베이스 접근 정책으로 검증한다.

## 6. MVP 2.0 작업 범위

### 6.1 포함 범위

#### 계정

- 이메일 매직링크 또는 사전에 선택한 소셜 로그인
- 로그인 상태 유지
- 로그아웃
- 최초 로그인 시 기본 프로필 생성

#### 프로젝트

- 프로젝트 생성
- 프로젝트 목록 조회
- 프로젝트 선택
- 프로젝트 정보 수정
- 프로젝트 보관 처리
- 최근 사용 프로젝트 기억

#### 기록

- 프로젝트에 기록 생성
- 사진 한 장 촬영 또는 앨범 선택
- 제목, 부제, 본문 입력
- 기록일 입력 및 수정
- 기록 저장
- 저장된 기록 조회
- 기록 수정
- 기록 삭제
- 프로젝트별 최신순 타임라인

#### 이미지 발행

- 저장 전 또는 저장 후 영수증 미리보기
- PNG 생성
- iOS 지원 환경에서 공유 시트 호출
- 그 외 환경에서 PNG 다운로드

#### UX 및 안정성

- 모바일 반응형 UI
- 빈 화면, 로딩, 오류, 저장 완료 상태
- 사진 업로드 진행 상태
- 지원하지 않는 파일과 용량 초과 안내
- 저장하지 않고 작성 화면을 나갈 때 이탈 경고
- 연속 저장에 대한 중복 요청 방지

### 6.2 조건부 범위

다음 기능은 공개 기록 운영이 실제로 필요한 경우 MVP 2.1에서 구현한다.

- 사용자의 공개 승인 요청
- 관리자 승인·반려 화면
- 반려 사유 입력
- 승인된 기록의 공개 페이지
- 승인 후 공개 중지
- 검토 이력 저장

### 6.3 제외 범위

- 기록당 여러 장의 사진
- 동영상 업로드
- 공동 프로젝트와 멤버 초대
- 댓글, 좋아요, 팔로우
- 사용자 간 메시지
- 마크다운 편집기
- 주간·월간 자동 요약
- PDF 일괄 내보내기
- 네이티브 모바일 앱
- 완전한 오프라인 작성과 동기화
- 유료 결제와 구독
- 관리자의 사용자 비공개 기록 직접 수정

## 7. 정보 구조 및 화면 명세

### 7.1 전체 화면 구조

```text
서비스 진입
├── 로그인
└── 로그인 완료
    ├── 프로젝트 목록
    │   ├── 프로젝트 생성
    │   └── 프로젝트 상세
    │       ├── 기록 타임라인
    │       ├── 기록 작성
    │       └── 기록 상세
    │           ├── 기록 수정
    │           └── 영수증 미리보기
    ├── 내 계정
    └── 관리자
        └── 공개 승인 요청 목록
```

### 7.2 로그인 화면

#### 목적

사용자를 식별하고 개인 데이터 공간에 접근시킨다.

#### 구성

- 서비스명과 한 줄 소개
- 로그인 버튼
- 개인정보 및 이용 안내 링크
- 로그인 처리 중 상태
- 로그인 실패 및 만료 안내

#### 수용 기준

- 로그인 성공 시 프로젝트 목록으로 이동한다.
- 이미 로그인한 사용자는 로그인 화면을 건너뛴다.
- 인증 실패 시 원인과 재시도 방법을 표시한다.

### 7.3 프로젝트 목록 화면

#### 목적

사용자가 기록할 프로젝트를 빠르게 선택하거나 새 프로젝트를 만든다.

#### 구성

- 사용자 인사 또는 계정 메뉴
- 최근 사용 프로젝트
- 전체 프로젝트 카드 목록
- 프로젝트별 이름, 부제, 기록 수, 최근 기록일
- 새 프로젝트 버튼
- 기록이 없는 빈 상태

#### 동작

- 프로젝트 카드를 선택하면 프로젝트 상세로 이동한다.
- 최근 수정된 프로젝트를 우선 표시한다.
- 보관된 프로젝트는 기본 목록에서 제외하고 별도 필터로 확인한다.

#### 수용 기준

- 사용자는 자신이 소유한 프로젝트만 볼 수 있다.
- 프로젝트가 없으면 생성 안내와 명확한 행동 버튼을 표시한다.
- 목록 재진입 시 최근 선택 프로젝트를 쉽게 찾을 수 있다.

### 7.4 프로젝트 생성·수정 화면

#### 입력 항목

| 항목 | 필수 | 제한 |
| --- | ---: | --- |
| 프로젝트명 | O | 1~50자 |
| 부제 | X | 최대 100자 |
| 대표 색상 | X | 제공된 프리셋 중 선택 |
| 커버 이미지 | X | MVP 이후 도입 가능 |

#### 동작

- 필수값을 입력해야 저장할 수 있다.
- 프로젝트명 앞뒤 공백을 제거한다.
- 저장 완료 후 프로젝트 상세로 이동한다.
- 삭제 대신 보관 처리를 우선 제공한다.

#### 수용 기준

- 동일 사용자가 같은 이름의 프로젝트를 만들 수 있으나 혼동 가능성을 안내할 수 있다.
- 다른 사용자의 프로젝트를 수정할 수 없다.

### 7.5 프로젝트 상세 화면

#### 목적

프로젝트 정보와 누적 기록을 한곳에서 확인한다.

#### 구성

- 프로젝트명과 부제
- 프로젝트 편집 메뉴
- 새 기록 작성 버튼
- 기록 수
- 기록 타임라인
- 날짜 또는 최신순 정렬
- 기록이 없는 빈 상태

#### 기록 카드

- 대표 사진 또는 사진 없음 상태
- 기록 제목
- 부제
- 기록일
- 본문 일부
- 공개 상태가 도입된 경우 상태 배지

#### 수용 기준

- 기록은 기본적으로 기록일 기준 최신순으로 표시한다.
- 기록 카드 선택 시 기록 상세로 이동한다.
- 데이터 조회 실패 시 재시도 기능을 제공한다.

### 7.6 기록 작성·수정 화면

#### 입력 항목

| 항목 | 필수 | 제한 및 기본값 |
| --- | ---: | --- |
| 프로젝트 | O | 진입한 프로젝트를 기본 선택 |
| 사진 | X | 1장 |
| 제목 | O | 1~80자 |
| 부제 | X | 최대 120자 |
| 본문 | O | 1~2,000자 |
| 기록일 | O | 현재 날짜·시간 기본값, 수정 가능 |

#### 사진 UX

- `촬영하기`와 `앨범에서 선택` 행동을 이해할 수 있게 제공한다.
- 선택한 사진을 즉시 미리보기로 표시한다.
- 사진 교체와 제거를 제공한다.
- 업로드 전에 지원 형식과 용량을 검사한다.
- 필요 시 클라이언트에서 긴 변 기준 크기를 축소하고 압축한다.
- 업로드 진행, 성공, 실패 상태를 표시한다.

초기 지원 형식은 JPEG, PNG, WebP를 권장한다. HEIC는 브라우저와 후속 이미지 처리 호환성을 검증한 뒤 지원 여부를 확정한다.

#### 저장 UX

- 저장 버튼은 필수값이 유효할 때 활성화한다.
- 저장 중에는 버튼을 비활성화해 중복 요청을 막는다.
- 저장 성공 후 상세 화면으로 이동하고 완료 상태를 표시한다.
- 사진 업로드 또는 데이터 저장 실패 시 작성 내용은 화면에 유지한다.
- 변경 내용이 있는 상태에서 이탈하면 확인 안내를 표시한다.

#### 수용 기준

- 사용자는 자신이 소유한 프로젝트에만 기록을 저장할 수 있다.
- 사진 없이도 기록을 저장하고 영수증을 만들 수 있다.
- 제목과 본문이 비어 있으면 저장할 수 없다.
- 수정 시 기존 데이터가 입력 폼에 표시된다.
- 수정 실패 시 기존 서버 데이터가 손상되지 않는다.

### 7.7 기록 상세 화면

#### 구성

- 프로젝트 정보
- 사진
- 제목과 부제
- 본문
- 기록일
- 작성일 및 수정일
- 수정 버튼
- 삭제 메뉴
- 이미지 만들기 버튼
- 공개 기능 도입 시 공개 요청 버튼과 상태

#### 수용 기준

- 소유자 이외에는 비공개 기록에 접근할 수 없다.
- 삭제는 확인 과정을 거친다.
- 삭제 완료 후 프로젝트 상세로 이동한다.

### 7.8 영수증 미리보기

#### 목적

웹 기록과 공유용 이미지 결과를 분리하고 발행 전에 결과를 확인하게 한다.

#### 구성

- 프로젝트명
- 프로젝트 부제 또는 기록 부제
- 기록일
- 제목
- 사진
- 본문
- 서비스명
- PNG 저장 또는 공유 버튼

#### 동작

- 미리보기는 저장된 데이터 또는 현재 작성 중인 데이터를 사용한다.
- 긴 텍스트는 이미지 영역을 넘지 않도록 줄 수 또는 글자 수를 제한하고 안내한다.
- iOS에서 파일 공유를 지원하면 공유 시트를 우선 사용한다.
- 공유 API를 사용할 수 없으면 PNG 다운로드로 대체한다.

#### 수용 기준

- 한글과 영문이 이미지에 정상적으로 출력된다.
- 사진 유무와 관계없이 이미지 생성이 가능하다.
- 같은 기록으로 다시 발행해도 일관된 결과가 생성된다.

## 8. 공개 승인 기능 명세

이 절은 MVP 2.1 조건부 범위다.

### 8.1 상태 정의

| 상태 | 설명 |
| --- | --- |
| `private` | 사용자에게만 보이는 기본 상태 |
| `pending` | 사용자가 공개 승인을 요청한 상태 |
| `approved` | 관리자가 승인하여 공개 가능한 상태 |
| `rejected` | 관리자가 사유와 함께 반려한 상태 |
| `unpublished` | 승인 후 운영상 사유로 공개 중지된 상태 |

### 8.2 상태 전이

```text
private ──공개 요청──> pending
pending ──승인──────> approved
pending ──반려──────> rejected
rejected ──수정/재요청──> pending
approved ──공개 중지──> unpublished
unpublished ──재승인──> approved
```

사용자가 승인된 기록의 공개 대상 내용을 수정하면 다시 `pending`으로 전환하는 것을 원칙으로 한다.

### 8.3 관리자 화면

- 검토 대기 건수
- 요청일 기준 목록
- 사용자, 프로젝트, 기록 미리보기
- 승인
- 반려 및 반려 사유 입력
- 공개 중지
- 상태 변경 이력

### 8.4 운영 원칙

- 관리자는 원문을 직접 고치기보다 반려 사유를 전달한다.
- 관리자 조치에는 관리자 ID와 처리 시각을 기록한다.
- 반려 사유는 사용자에게 노출한다.
- 공개 페이지에는 승인된 데이터만 조회되도록 데이터 정책을 적용한다.
- 승인 상태는 일반 사용자가 임의로 변경할 수 없다.

## 10. 데이터 접근 정책

### 10.1 일반 사용자

- 본인이 소유한 프로필만 조회하고 허용된 필드만 수정할 수 있다.
- 본인이 소유한 프로젝트만 생성, 조회, 수정, 보관할 수 있다.
- 본인이 소유한 프로젝트에 속한 기록만 생성, 조회, 수정, 삭제할 수 있다.
- 본인 경로의 사진만 업로드, 조회, 교체, 삭제할 수 있다.
- 관리자 역할과 승인 상태를 직접 변경할 수 없다.

### 10.2 관리자

- 관리자 화면 접근 시 관리자 역할을 검증한다.
- 공개 승인 요청에 필요한 데이터만 조회할 수 있다.
- 승인, 반려, 공개 중지 상태 변경을 수행할 수 있다.
- 모든 관리 작업을 검토 이력으로 남긴다.

### 10.3 스토리지 경로

사진은 다음과 같이 사용자 ID를 포함하는 경로를 권장한다.

```text
records/{owner_id}/{project_id}/{record_id}/{file_name}
```

- 비공개 버킷을 기본으로 사용한다.
- 로그인 사용자와 접근 정책을 검증한 요청에만 파일을 제공한다.
- 공개 이미지가 필요하면 승인된 기록에 한해 제한된 공개 URL 또는 서명 URL 정책을 사용한다.

## 11. 기술 및 배포 범위

### 11.1 권장 구성

| 영역 | 권장안 |
| --- | --- |
| 프론트엔드 | 정적 HTML/CSS/JavaScript 또는 정적 빌드 가능한 경량 SPA |
| 정적 배포 | GitHub Pages 유지 |
| 인증 | Supabase Auth |
| 데이터베이스 | Supabase Postgres |
| 사진 저장 | Supabase Storage |
| 접근 제어 | Row Level Security |
| 소스 관리 | 현재 공개 GitHub 저장소 |

### 11.2 공개 저장소 원칙

공개 저장소에는 다음 항목을 포함할 수 있다.

- 프론트엔드 소스
- 공개용 환경 변수 예시
- 데이터베이스 마이그레이션
- 접근 정책 정의
- 배포 설정

다음 항목은 포함하지 않는다.

- 서비스 역할 키
- 데이터베이스 비밀번호
- 관리자용 비밀키
- 개인 액세스 토큰
- 실제 사용자 데이터와 사진

브라우저에서 사용하는 공개 키는 노출 자체를 비밀로 간주하지 않고, 데이터 보호는 인증과 접근 정책으로 보장한다.

### 11.3 환경 분리

최소한 다음 환경을 구분한다.

- 로컬 개발 환경
- 운영 환경

관리자 승인과 공개 페이지가 추가되거나 실제 사용자가 늘어나면 별도의 스테이징 환경을 추가한다.

## 12. 비기능 요구사항

### 12.1 보안

- 모든 데이터 테이블과 스토리지에 사용자별 접근 정책을 적용한다.
- 비밀키를 클라이언트 코드에 포함하지 않는다.
- 사용자 입력을 HTML로 직접 삽입하지 않는다.
- 이미지 MIME 형식과 파일 크기를 클라이언트와 스토리지 정책에서 검증한다.
- 관리자 권한 변경 경로를 일반 사용자에게 허용하지 않는다.

### 12.2 성능

- 프로젝트 목록과 기록 목록은 필요한 데이터만 조회한다.
- 기록 목록의 이미지는 원본 대신 썸네일 사용을 권장한다.
- 초기 화면에서 모든 원본 사진을 한 번에 내려받지 않는다.
- 기록이 증가할 것을 고려해 목록 페이지네이션 또는 더 보기를 지원할 수 있게 설계한다.

### 12.3 접근성

- 모든 입력 요소에 연결된 레이블을 제공한다.
- 키보드만으로 주요 기능을 사용할 수 있어야 한다.
- 색상만으로 상태를 구분하지 않는다.
- 상태 메시지는 보조 기술이 인식할 수 있어야 한다.
- 텍스트와 배경은 적절한 명도 대비를 갖는다.

### 12.4 호환성

최소 검증 대상은 다음과 같다.

- 최신 iOS Safari
- 최신 Android Chrome
- 최신 데스크톱 Chrome
- 최신 데스크톱 Safari

### 12.5 개인정보

- 사진과 기록의 저장 위치 및 이용 목적을 사용자에게 안내한다.
- 계정 삭제 도입 시 프로젝트, 기록, 사진의 처리 정책을 함께 정의한다.
- 관리자 검토가 필요한 경우 검토 대상과 범위를 공개 요청 전에 안내한다.

## 13. 오류 및 예외 처리

| 상황 | 기대 동작 |

## 17. 출시 완료 기준

- 사진 없이도 기록 저장과 PNG 발행이 가능하다.
- 사진이 있는 기록도 PNG로 정상 발행된다.
- iOS 공유 및 데스크톱 다운로드가 정상 동작한다.
- 모바일 핵심 화면에서 기능을 가리는 레이아웃 오류가 없다.
- 인증, 데이터 저장, 사진 업로드 실패 상태가 사용자에게 안내된다.
- 공개 저장소와 배포 결과물에 비밀키가 포함되지 않는다.

## 18. 사전 결정 필요 항목

개발 착수 전에 다음 항목을 확정해야 한다.

1. 로그인 방식: 이메일 매직링크, Google, GitHub 중 우선 지원 방식
2. 기록 사진 최대 용량과 압축 기준
3. HEIC 사진 지원 범위
4. 프로젝트 삭제 대신 보관만 제공할지 여부
5. 기록 삭제의 복구 가능 기간
6. 공개 갤러리 도입 여부
7. 관리자 승인 기능을 MVP 2.0에 포함할지 MVP 2.1로 분리할지 여부
8. 공개 승인 후 사용자가 기록을 수정할 때의 재검토 정책
9. 개인정보 처리 안내 및 계정 삭제 정책
10. 현재 단일 HTML 구조 유지 또는 정적 빌드 가능한 프론트엔드 구조 도입 여부
